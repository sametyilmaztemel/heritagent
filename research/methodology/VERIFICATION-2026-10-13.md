| V1 | As specified, no mining pair can exist | holds, overstated | P0 / P0 | P0 (critical-path design gap; the code is not broken). The Trait Miner accepts only success/failure MiningPairs that have identical `task` text and identical benchmark/split/environment provenance (traits/miner/inputs.py). As currently written, the EXP-0001 G0 lifetime runs once per T_mine instance per mining seed (design:85). The shipped runtime fixes the lifetime at temperature 0 (runtime/loop.py:174, no override), and ALFWorld is deterministic. So the specified protocol gives no same-instance success/failure pair. Pairs could arise only by accident, in one of two ways. (a) Different game instances happen to share identical task text, which the code accepts because provenance carries no instance id; whether this can happen depends on what the unbuilt ALFWorld adapter passes as `task`, and such pairs would be few and confounded by scene layout. (b) Pairing across the 3 mining seeds, which breaks their independence and at temp 0 yields identical trajectories anyway. The pairing and lifetime sampling policy was explicitly deferred to #13 (inputs.py docstring; #9 handoff) but was never pre-registered. Two things are ambiguous: whether the Critic's own pairing intent was same-family rather than same-task, and whether the 0.7 "mining temperature" applies to the lifetime. An ADR must fix the following before EXP-0001 can produce candidates: the lifetime temperature and seed derivation; the number of rollouts per task; the pairing unit (same instance vs same family); instance identity in the pair check; and the temp-0 definition of "G0-solved" used for T_reg. |
| V2 | Arm C promoted w.p. 0.002-0.09; modal empty C | holds, overstated | P0 / P1 | The gate requires all five stages to pass: replay (>=3/5 successes with the trait and net >=2), stage-2 bootstrap (in effect >=4 net wins of 20), in-scope and out-of-scope (each net >=0 of 10), and T_reg (<=1 failure of 40). False promotion is negligible, but false rejection compounds. Under an explicit task-independence model (not data), a trait with a true +20pp effect is promoted with probability of about 0.002 to 0.2 when the noise loss rate is 2.5-5%, or about 0.14 with no losses. The low end requires T_reg flips spread evenly over G0 successes (about 6-12% per task). The result depends mainly on the unmeasured flip rate f and on stage 2. E[\|C\|] per seed ranges from about 0 to 2 for +20pp candidates, and P(\|C\|=0) is large (about 0.2 to 0.75). An empty arm C is therefore a plausible outcome, not a certainty. Separately, and verified from the documents, the pre-registered H2 rule (design:66 / YAML:100) has no non-degeneracy clause. With \|C\|=0, so C=A=G0 and reg(C)=0, H2 is formally "supported" whenever B is significantly harmful. That supports "veto/no inheritance beats inherit-all", not causal selection. H1 (C-A) and the SPEC §29 / #13 M0 success criterion would fail in that case and expose the result, but the H2 label itself would be an overclaim. Fix before #6: an ADR adding an H2 non-empty-arm-C condition and a pre-declared "gate-as-veto" outcome, plus a disjoint-pool calibration pilot to measure d0, f0 and G0 success, so the stage-pass counts #6 asks for are grounded. |

## 5. genome_id ADR draft critique

Draft: `research/proposals/ADR-draft-canonical-genome-id.md` (PROPOSED only; no rule invented in code).

Golden vector reproduced (G-ab49fa967c969a10), conditional on the identity domain always containing `skills: []` and `regulation: {}`. All six issue #22 checklist items are covered. Remaining gaps: no test for a schema_version or id_rule change in the I8 diff-consistency check (diff_genomes ignores schema_version, so I8 as written would raise), and no test for H-d parent self-pointer or cycle behaviour pending the Critic's decision.

Blocking issues (3), all edited into the draft; decisions remain with Research/Critic and the owner:
1. Integral-float `version` bypasses the identity rule. jsonschema accepts `1.0` as integer; `loader._check_gene_ref` compares `int(...) != ref.get('version')`, which is False for 1 vs 1.0; `canonical_json` then writes `1.0` instead of `1`, so identical heritable content gets a different id (breaks "same heritable content -> same id"). Edit: new §5.3 bullet and an extension to test 8. Open choice: reject `type(version) is not int` in `load_genome` (proposed) or normalize.
2. Genotype-only ids make the genome-level `parent` pointer ambiguous. `parent` has no pattern; ADR-0001 D3, #16 and ADR-0002 say lineage is derivable from provenance / parent pointers. Under the proposal a clonal arm-A G1 gets parent==genome_id, a reverting mutation makes id-level ancestry cyclic, and convergent lineages merge. The draft's claim of no D3 conflict was removed. Edit: hazard H-d with options (i) document parent as a genotype id, (ii) add a node-level parent reference such as the parent's manifest_sha256 (schema change), (iii) L1; §11 now states the D3 tension; Q0 references H-d.
3. Pooling repeated measurements under one genotype key conflicts with the locked `determinism_policy.no_pseudo_replication: true`. Arms A and C collide when C promotes 0 candidates; B and C collide when all K=10 pass; duplicate deterministic runs would be duplicates, not samples (SPEC §34 risk). Edit: caveats in §4.3 and §12 (pool only across distinct instances; dedupe on (genome_id, instance, condition)); §14 evaluation-store row notes run records need arm/mining-seed context the D7 key lacks.

Other edits (non-blocking, 16 items): evidence base moved to 6014bc7; collision arithmetic corrected (16 hex gives 2.7e-6 at 10^7, above 1e-6; 17 hex needed; Q1 stays open); `canonical_bytes` disambiguated (trajectory vs registry); skills/regulation keys always present; non-ASCII-field claim corrected (lineage_id, parent, source_trajectory, cig_record are also unconstrained); `parent` pattern is new, cig schema has no parent; `build_g0_seed_genome(registry)` exists and G0_GENOME_ID is unused elsewhere; gate.py genome_id at line 741, interaction.py:272/276 also uses the base id; O3 scope note; Q4 caveat that tightening eag/0.1 in place changes what the locked manifest reference means; I1 cross-CPython-version claim tested only indirectly via the golden vector.
