## Mechanism

- **Setting (§2).** A skill-augmented coding agent on a fixed LLM (DeepSeek-V4-Flash for every agent and baseline, §4.5; no weight training anywhere). Skill bank D = {s_1..s_n}; a retriever picks S_x ⊆ D per task; τ ~ π(·|S_x, x) (Eq. 1). Evolution is D' = U(D, τ) (Eq. 2), with the stated objective of an optimal D* maximizing expected success "across the distribution of all tasks".
- **Stage 1 — trace collection (§3.1).** Instrument the agent; simplify traces by dropping heavy tool outputs (full find/grep results, file contents, info-level logs) while keeping commands, paths, key errors and reasoning blocks. ("Causal" appears here only in "high-level causal analysis" of traces.)
- **Stage 2 — evolution proposal generation (§3.2).** Triggered by *failures* only.
  - *Failure diagnosis:* hierarchical classification of the failure as navigation / reasoning / execution failure, then a root-cause hypothesis. Two evolution types: "general capability enhancement" (workflow-level) vs "reusable problem pattern" (pattern + actionable strategy).
  - *Skill Relation Graph (SRG):* directed graph G = (V, E), nodes = skills, typed edges r ∈ {**dependency** ("v_j relies on assumptions, or results produced by skill v_i"), **co-usage** (complementary, better together or in a given order), **conflict** (incompatible guidance; "should not be activated simultaneously")}. "GSE treats both the skill contents and their relationships as first-class objects of evolution." For a proposed update, GSE looks at SRG neighbours plus metadata-retrieved candidates (capability category, task type, execution stage), asks the update agent whether assumptions / intermediate outputs / applicability / interaction patterns change, and if so emits **auxiliary evolution proposals** that co-evolve the affected skills and edges ("relationship-aware propagation").
  - *DSL proposal (§3.2.3):* "the target skill, the edit operation, the concrete content to be updated, the rationale, the expected behavior after the update, and the relation changes".
  - *Local validation:* apply the proposal to a temporary candidate skill bank and replay the originating failure case; "Proposals that fail to resolve their originating failure are discarded immediately."
- **Stage 3 — skill generalization (§3.3, Algorithm 1).**
  - *Clustering:* proposals that modify existing skills are grouped by the set of modified skills (clustering key = S_p); proposals that add new skills are clustered by semantic similarity of rationale and expected effect.
  - *Consolidation:* a merge agent extracts common patterns per cluster, removes case-specific details, resolves redundant/conflicting updates, and instantiates the abstraction on G as a candidate bank G_c.
  - *Replay-driven validation (§3.3.2):* replay set R_c = "historical cases in which the affected skills were previously activated" (for modifications) or "all cases that generated the clustered proposals" (for new skills). "A candidate skill bank is accepted only if it maintains or improves performance across the replay cases." Algorithm 1 line 22: "if o_c preserves or improves performance then G ← G_c". Clusters are processed sequentially, so each accepted cluster changes the incumbent for the next.
- **Infrastructure (§4.5).** LangChain v1.1.1; traces, replay outcomes and update states in SQLite; "the skill bank is versioned with Git worktree", which "makes every accepted skill version reproducible".
- **Not specified anywhere in the text:** the performance metric used inside replay (pass rate? per-case?), replay-set sizes, how "maintains" is decided (no tolerance, no test), number of proposals generated / locally validated / accepted per cluster, final bank size, how many evolution passes, how retrieval works, and whether code is released (no repository link for GSE in the text; the only GitHub links are to Anthropic Skills and LangChain).

## Results

- **Setup (§4).** Two tasks, both one-project-held-out (each run holds out all cases of one project; the rest are used for evolution):
  - Bug-revealing test generation: 108 manually verified buggy focal methods from 9 Java projects of Multi-SWE-Bench.
  - False-positive bug-report filtering: IndustrialBugs, 500 reports (132 real bugs, 368 false alarms) from 8 ByteDance Go repositories, labelled by the original committers.
  - Base harnesses: OpenHands and mini-SWE-agent (the authors added a skill-loading interface to mini-SWE-agent). Same tools, LLM, per-task budget across techniques.
  - Comparators: vanilla agent; Human Skills (17 skills written by 6 senior engineers); Live-SWE-agent (adapted from tool evolution to skill evolution); Trace2Skill (Ni et al. 2026, released artifacts, I/O adapted).
  - Temperature 0, apparently **one run per configuration** ("we set the LLM temperature to zero ... to ensure deterministic evaluation", §7). No seeds, CIs or significance tests anywhere.
- **Table 1 (test generation, P/R/F1).** OpenHands: base .17/.06/.08; Human .33/.10/.16; Live-SWE .31/.17/.22; Trace2Skill .31/.14/.19; **GSE .35/.28/.31**. mini-SWE-agent: base **.48**/.19/.28; Human .42/.19/.26; Live-SWE .43/.21/.29; Trace2Skill .41/.22/.29; **GSE .55/.29/.38**.
- **Table 2 (FP filtering).** OpenHands: base .25/.73/.37; Human .29/.80/.42; Live-SWE .28/.82/.42; Trace2Skill .29/.84/.43; **GSE .55/.95/.70**. mini-SWE-agent: base .23/.78/.36; Human .25/.81/.38; Live-SWE .26/.83/.39; Trace2Skill .25/.84/.39; **GSE .30/.97/.46**.
- **Table 3 (ablation, OpenHands only).** Test-gen F1: w/o graph .27, w/o gen .27, full .31. FP-filter F1: w/o graph .59, w/o gen .54, full .70. "w/o gen" = proposals merged after *local* validation only, "without cluster-based consolidation or replay-driven validation" — so consolidation and the regression-replay gate are removed **together** and their effects are not separable.
- **Table 4 (tokens, macro-averaged).** Evolution per case: Trace2Skill 357.64K vs GSE 401.55K (+12.28%). Execution per case: base 489.31K; Human 620.58K; Live-SWE 613.61K; Trace2Skill 619.65K; GSE 593.21K (+21.2% vs base, fewest among skill methods).
- **Table 5 (industrial bug-triage agent, FP filtering).** Internal .29/.83/.43; +Human .30/.83/.44; +GSE .56/.97/.71. Note that GSE was *run* on this agent (evolution re-done), not a transfer of an already evolved bank.
- **My recomputation of the headline ranges.** The ranges mix comparator sets, although the abstract says "Compared with existing evolution techniques":
  - Test-gen recall upper bound 180.0% = 0.28 vs **Human Skills** 0.10; against the two evolution techniques the maximum is +100% (0.28 vs Trace2Skill 0.14). F1 upper bound 93.8% = 0.31 vs Human 0.16.
  - FP-filter recall upper bound 19.8% = 0.97 vs Human 0.81 (vs evolution techniques max +16.9%).
  - Industrial 61.4% F1 is vs Human Skills (vs base it is +65.1%).
  - mini-SWE-agent test-gen precision "+27.9% over the strongest baseline" uses 0.43 (Live-SWE-agent); the vanilla base agent has 0.48, i.e. all three skill baselines *lowered* precision vs no skills, and GSE's margin over the base is +14.6%.
  - These are labelling issues; the direction of the results is unaffected. All values are single-run point estimates on 108 / 500 cases, so small gaps (e.g. OpenHands test-gen precision .35 vs .33) cannot be separated from noise.
- **Threats to validity (§7)** cover agent/language/task generality, implementation errors, LLM randomness (temperature 0) and leakage (one-project-held-out; no generated test matches reference tests; proprietary code excluded from public training corpora). No limitations section beyond that; cost of replay not broken out from evolution cost.

## What remains different

- **Unit of validation and admission.** GSE validates and admits *consolidated clusters* (bank deltas rewritten by a merge agent), not individually ablated traits; there is no estimate of any single trait's contribution C(t|G) and no Shapley/attribution step. HeritAgent's CIG asks whether a specific lifetime-acquired trait caused success and validates exactly the object that gets assimilated.
- **Evidence type.** GSE's gate is a replay pass/no-worse check on the agent's own historical cases (in-distribution, same projects), at temperature 0, with no statistics and ties admitted. CIG requires replay on unseen same-family variants, controlled with/without ablation with a CI lower bound, in-scope and out-of-scope held-out stages, and a regression budget on a fixed suite.
- **No inheritance.** One evolving bank per agent per run; no somatic store distinct from a heritable genome, no assimilation event across generations, no descendant adaptation cost, no lineage graph.
- **Genome scope.** Skills only (plus relations). No policies (planner, retry, tool selector), no declarative expression conditions over runtime counters, no model-independent expression layer.
- **Gate placement.** The gate logic is not described as outside the evolvable artifact, but nothing in GSE lets the agent edit it either; this is not a point of difference worth claiming.

## Changed vs abstract-level assessment

There was no abstract-level chain vector for GSE: Round 2 listed it in §2.12 as a "commit-gate competitor named by deep reads (titles confirmed on arXiv, not read)" and in §3 item 14 as cited concurrent work for consolidation / structural-growth control of skill libraries.

- **Element 4 (causal gate): threat DOWN vs the "commit-gate competitor" label.** The gate is a performance replay check with zero-margin non-inferiority. It is weaker than GRASP (net fix−regression > 0 plus R(c) ≤ R0) and SAGE (paired test with abstain), has no ablation or attribution, and admits consolidated deltas rather than individual traits. It adds one more member to the crowded within-lifetime pre-persistence cluster (§3 items 9–11) but does not touch the "trait-level causal evidence as prerequisite for germline assimilation" clause.
- **Element 3 / CIG interaction stage: threat UP (not anticipated by the ledger).** Typed dependency / co-usage / conflict edges between skills, treated as first-class evolvable objects with propagated auxiliary updates, and regression replay targeted at cases where the affected skills were activated, are prior art HeritAgent did not list. HeritAgent must not present typed inter-trait relations, conflict constraints between genes, or interaction-targeted regression selection as new.
- **Element 5:** confirms "consolidation / abstraction before admission" as prior art (already in §3 item 14 by citation; now verified).
- **Overall:** MEDIUM for specific sub-claims (typed trait relations; replay-gated consolidation), consistent with how comparable Round-2 entries were calibrated (e.g. SkillEvoReg, GRASP). It does **not** change the Round-2 chain verdict: no work found implements all six elements, and GSE has no inheritance at all.
- **Fairness note in GSE's favour:** its ablation (FP filtering F1 0.70 → 0.54 without generalization; OpenHands only, single run, confounded with consolidation) is one more datum that a regression-replay gate plus consolidation beats local-only acceptance within one lifetime — the same direction as VaG/GRASP evidence against H2-as-novelty. It also shows that evolved skills can generalize to held-out *projects* under a frozen model, a weak precedent for the in-scope generalization idea.
- **Fairness note against GSE:** single-run point estimates, comparator mixing in the headline ranges, undocumented replay metric and acceptance counts, no code link. Its numbers should not be used as effect-size priors for EXP-0001.

## Implications for EXP-0001 / CIG (all flagged; nothing changed here)

1. **Arm B′ candidate operationalization (requires ADR — amendment to ADR-0002).** GSE's rule is a clean, published "performance-gated" acceptance rule from the coding-agent literature: admit iff (a) the candidate resolves its source episode on replay and (b) success on the regression cases where the relevant skill was expressed does not drop (Δ ≥ 0). It is cheaper and weaker than the GRASP/VaG/SAPO options already listed in ledger §5 item 1, so it would serve as a *lower* B′ variant (a "replay-only gate"). If one B′ is pre-registered, GRASP-style remains the stronger reviewer-natural choice; GSE-style could be a secondary arm or an analysis reusing CIG stage-1 and stage-4 data (stage 1 already replays the source task; stage 4 already reruns T_reg), so it may be computable at near-zero extra cost from arm-C gate logs — **requires ADR if used as an arm; pre-registration note if run as a secondary re-analysis**.
2. **Do not confound gate and consolidation (requires ADR when consolidation is introduced).** GSE removes consolidation and replay validation together in its ablation, so neither effect is identified. EXP-0001's candidate-set freeze (same frozen K = 10 candidates for B and C) already avoids this. If any merge/abstraction step is later added to the trait miner or the VTA (e.g. for H5 genome-bloat control), it must be applied identically across arms and ablated separately from the gate.
3. **Ties admitted (threshold change requires ADR; reporting does not).** GSE's "maintains or improves" is the same zero-margin tie admission as EXP-0001 stage-3 in-scope "Δ ≥ 0"; this reinforces ledger §5 item 4 (consider a paired per-item test with abstain or a small positive margin; report n01/n10 counts).
4. **Expression-conditioned regression selection (secondary analysis; requires ADR only if it replaces T_reg).** GSE selects regression cases where the affected skills were activated. CIG stage 4 uses a fixed T_reg (40) plus pairwise co-expression on 10 T_gate tasks. Reporting regression separately on the T_reg subset where the candidate trait actually fired would sharpen the regression signal (most T_reg tasks may never express a narrow trait, diluting τ_r). Expression logging already exists (stage-1 expression check).
5. **Typed interaction relations in the EAG (later ADR — ADR-0001 amendment).** The v0 interaction rule ("harmful pairs → keep the higher-contribution trait only") discards information that GSE keeps as a typed conflict edge. If populations / recombination are introduced, consider recording measured pairwise interactions as typed relations in the genome or lineage graph, citing GSE's SRG, and phrase any claim as "measured interaction records" rather than "typed inter-skill relations" (prior art).
6. **Statistics.** Nothing to adopt: GSE has no gate statistics or run-level uncertainty. Its temperature-0 single-run evaluation is the pseudo-replication-free extreme that EXP-0001 already handles better (cluster bootstrap over instances + 3 mining seeds).
