# EvoSkill — detailed notes

**Paper:** *EvoSkill: Automated Skill Discovery for Multi-Agent Systems* — Salaheddin Alzubi, Noah Provenzano, Jaydon Bingham, Weiyuan Chen, Tu Vu (affiliation shown in the arXiv HTML: Sentient, Virginia Tech). arXiv:2603.02766, v1 3 Mar 2026 (only version as of 2026-10-12), cs.AI (cross-list cs.MA); first-page footnote "Preprint. Work in progress." Code link given in the paper: github.com/sentient-agi/EvoSkill (**not opened** — the repo could not be reached from this environment; its contents are unverified). Reviewed 2026-10-12 from the **full arXiv HTML text** (v1), including Algorithm 1 and Appendices A–D. Found by the round-2 `causal-skill-validation` sweep; not in the ledger before this note.

## Mechanism

- **Setting:** Claude Code harness with Opus 4.5 as the executor model; **model frozen throughout** — "only the skill repository and agent metadata evolve across iterations". Builds directly on Feedback Descent (Lee, Boen, Finn 2025, arXiv:2511.07919): a frontier of candidates + accumulated textual feedback history driving an editor LLM.
- **Three agents:** *Executor* (runs tasks under the current program; base program has no skills); *Proposer* (reads the Executor's traces, predicted answers **and ground-truth answers**, diagnoses failures, chooses `create` vs `edit`, must consult a cumulative feedback history H of all past proposals, scores and verdicts — including DISCARDED ones); *Skill-Builder* (materializes the proposal into an Agent-Skills-format folder: `SKILL.md` with name/description trigger metadata, procedural instructions, optional Python/TypeScript helper scripts; bootstrapped with a skill-authoring meta-skill; the only agent with write access to the skills directory).
- **Loop (Algorithm 1):** parent p chosen round-robin from frontier G → evaluated on a training batch → samples below a score threshold (weighted multi-tolerance score < 0.8) form the failure set F (skip if empty) → Proposer proposes one skill create/edit → Skill-Builder builds candidate p̃ = parent config + new/revised skill → p̃ scored on validation set V → **admitted iff |G| < k OR score(p̃) > min score in G** (weakest member evicted when over capacity) → proposal + score + verdict appended to H. Returns argmax-score program after T iterations; early stop after N iterations without frontier improvement.
- **Frontier:** called a "Pareto frontier" in the abstract, but the algorithm is a **scalar top-k elitist set** (default K = 3, Appendix D) ranked on one validation score — there is no multi-objective Pareto dominance.
- **Representation / lineage (Appendix D):** each program = a git branch `program/...` whose only diff from the parent is skill folders + `.claude/program.yaml` (name, **parent pointer, generation counter = mutation depth from root**, system prompt, allowed tools, scores). Frontier tracked by git tags; rejected children's branches are deleted. Codebase fixed so that "performance differences between programs are attributable solely to their evolved skills". A prompt-only mutation mode also exists.
- **Data protocol:** LLM-classified categories → stratified disjoint train (failure mining) / validation (frontier selection) / test (never seen during evolution) splits.
- **Skill-merge configuration:** union of unique skills from independent runs; name/description collisions resolved by keeping the version from the highest-performing run. The paper does not describe any validation gate applied to the merged library.

## Results (single run per configuration — authors state no seed variance analysis)

- **OfficeQA** (246 Q over U.S. Treasury Bulletins; validation set = 17 examples ≈ 7%; training 5/10/15% = 12/24/36 examples; 1.5 epochs): exact match base 60.6 → 63.4 (5%), 65.8 (10%), 64.5 (15%), **merge-unique 67.9 in text/abstract (+7.3 pp) but 68.1 in Table 1** — internal inconsistency. Plateau / mild overfit beyond 10% acknowledged.
- **SealQA** seal-0 (111 Q, 10% train, 1.5 epochs): 26.6 → **38.7** (+12.1 pp). Validation-set size not stated.
- **Zero-shot transfer:** one skill (`search-persistence-protocol`) evolved on SealQA applied unchanged to a 128-question stratified sample of BrowseComp: 43.5 → **48.8** (+5.3 pp). Single skill, single run, post-hoc.
- No ablations (e.g., no Proposer-without-history, no ground-truth-free variant, no validation-gate-off variant); no per-skill contribution analysis; no regression analysis; gains reported as absolute points without CIs.

## Overlap vs HeritAgent chain

| Element | Coverage |
|---|---|
| 1. Lifetime-trajectory mining | **Full** — skills are proposed from the Executor's failure traces; edits to existing skills are trace-driven. Caveat: diagnosis uses ground-truth labels (supervised error analysis), and acquisition is an offline optimization loop over a labelled training split, not an agent's own deployment lifetime |
| 2. Somatic/germline separation | **Absent** — the candidate child exists on a branch only until one validation score is computed, then is either admitted (all its skills become the inherited configuration) or deleted. There is no persistent per-individual store whose contents are not passed on; the feedback history H is the optimizer's run-level log, not an agent's somatic memory. (Fair note: the "evaluate before admission" step is a one-shot candidate quarantine, which is the nearest analogue) |
| 3. Typed executable genome | **Partial** — discrete, versioned (git), executable (helper scripts) skill units with trigger metadata (≈ primitive regulation) plus a structured `program.yaml` (parent, generation, system prompt, tool permissions, scores). Stronger than MGM/DGM's raw code; but no typed gene schema (policy vs skill vs regulation), no per-trait provenance or validation record, no expression/interaction semantics |
| 4. Causal Inheritance Gate | **Partial (weak)** — there *is* a held-out-validation retention gate on a single-edit child, with a fixed codebase so the edit is the only difference. But: (a) comparison is against the **weakest frontier member, not the parent**, so it is not a paired with/without ablation of the edit, and a child that scores below its own parent can be admitted; (b) admission is **unconditional while the frontier is below capacity**; (c) one scalar score on a tiny validation set (17 items on OfficeQA), no CI/significance; (d) no attribution, no regression suite, no generalization stage beyond the same-distribution validation split, no interaction check. Transfer is measured post hoc, not gated. Contrary to the abstract's "retaining only skills that improve held-out validation performance", Algorithm 1 does not enforce improvement over the parent |
| 5. Selective assimilation | **Partial** — selection exists, but at whole-program level (top-k by scalar score); skills accumulate inside admitted programs without per-skill re-validation; the skill-merge configuration unions skills across runs with no stated gate. Selection is performance-based, not trait-causal |
| 6. Multi-generational, frozen weights | **Full as a mechanism** — frozen Opus 4.5, child inherits all parent attributes, parent pointers + generation counter give a reconstructible lineage tree. Same class as DGM/MGM: "generations" = mutation depth within one search run (1.5 epochs, K = 3 frontier); no distinct lifetimes, no descendants acquiring their own lifetime traits, no inheritance-specific metrics (descendant adaptation cost, genome bloat across generations) |

**Chain verdict:** does not implement the full chain. EvoSkill is best described as *Feedback-Descent / GEPA-style frozen-backbone search whose mutation unit is an Agent-Skills folder*, with a held-out-score elitist retention rule.

## Threat assessment (fair in both directions)

- **Real threat to wording, not to the integrated claim.** EvoSkill is the cleanest published example (Mar 2026) of "LLM-mined skills retained only after held-out validation, model frozen, with lineage". Any HeritAgent sentence of the form "we gate skill retention on held-out evidence" or "we inherit validated skills without weight updates" is **already done** by EvoSkill (and by LOGOS's held-out "promotion"; and SkillForge for verification). Medium threat is the right level.
- **Where the gap is genuine:** (i) no somatic/germline architecture; (ii) the gate is whole-program, scalar, frontier-relative and same-distribution — not trait-level controlled ablation vs the parent, attribution, cross-environment generalization or regression protection; (iii) the genome is a skills folder + prompt, not a typed functional genome with regulation; (iv) no study of inheritance across lifetimes.
- **Where EvoSkill is stronger than HeritAgent currently is:** working implementation on a frontier model with real benchmark gains and a zero-shot transfer demonstration; git-backed lineage infrastructure that is reproducible by construction. HeritAgent has no comparable published results yet (SPEC §34: do not imply superiority).
- **Its reported evidence is weak** (single runs, n = 17 validation, a 67.9/68.1 mismatch, round-robin parent selection in §2.2 vs "highest-scoring program" as parent in Appendix D) — worth noting in Related Work only as "gains reported from single runs", not as a criticism-led argument.

## Consequences for HeritAgent

- **Ledger §3 additions (do-not-claim):** (a) held-out-validation-gated retention of LLM-generated skills under a frozen model (EvoSkill; also LOGOS); (b) git-backed program lineage with parent pointers / generation counters as agent-genome versioning infrastructure (EvoSkill App. D); (c) zero-shot cross-benchmark transfer of evolved skills as a demonstration in itself.
- **Positioning sentence:** EvoSkill retains *programs* whose single validation score beats the weakest frontier member; CIG admits a *trait* into the germline only if its paired with/without contribution relative to the parent genome survives ablation, generalization (in/out of scope) and regression stages, and rejected traits stay somatic. Gloss EvoSkill's mechanism as **performance-gated selection**, ours as **causally-gated assimilation**.
- **Experiment design (recommendation, not a requirement):** EXP-0001 currently contrasts A (none), B (unrestricted, SkillRL-style) and C (CIG). A reviewer will ask whether CIG beats a *simple held-out-score gate*. An EvoSkill-style arm — admit a candidate if the genome-with-candidate improves a single held-out validation score, no per-trait ablation/regression stages — would isolate the value of CIG's causal stages over "any validation gate". Candidate for EXP-0001 extension or a follow-up EXP; budget impact not estimated here.
- **H5 motivation:** Algorithm 1's frontier-relative admission can admit a child that regresses relative to its parent — a concrete, citable example of why CIG compares against the parent genome and runs a regression suite (τ_r).
- **Merge result as arm-B evidence:** the skill-merge union of independently evolved skills scored best on OfficeQA — a data point that unrestricted unions are not necessarily harmful in that regime (consistent with EXP-0001 threat §6.5 "if arm B ≈ arm C that is a finding").
- **Sweep follow-up:** EvoSkill cites GEPA (arXiv:2507.19457; reflective mutation + Pareto candidate selection) and Feedback Descent (arXiv:2511.07919), neither of which is in the ledger. Not reviewed here — flag for the next sweep round rather than citing from this note.
