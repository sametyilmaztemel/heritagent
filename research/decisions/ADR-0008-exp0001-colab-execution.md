# ADR-0008 — EXP-0001 execution on one Colab A100 80 GB: parallel episodes, active run time, run mirror

Date: 2026-10-14 · Status: **ACCEPTED by the owner** for its three decisions (Samet, 2026-10-14, explicit answers in chat: the 96-hour cap counts active run time only, D2; only an A100 80 GB is admitted, D1; episodes run in parallel, D3). The mechanism of D3 and D4–D6 are builder-2's engineering within those decisions; they change no threshold, budget, seed, allocation or arm. The owner accepted them as well on 2026-10-15, after the second review round (explicit answer in chat, "Kabul", to a question that named D3's mechanism, D4's server settings, context and pinned library versions, D5 and D6). On 2026-10-14 the owner also removed Codex from the process: builder-2 now holds the Critic's duties (different-model reviews), and the owner decides. No Codex review is requested. Artifacts: `evaluation/exp0001/` (`ledger.py`, `episodes.py`, `gate_runner.py`, `lifetime.py`, `pipeline.py`, `mirror.py`, `serving.py`, `backends.py`, `data.py`, `pilot_run.py`, `cli.py`), `runtime/model_adapters/openai_server.py`, `notebooks/`, the manifest's `compute_cap.wall_clock_basis` and `run_protocol.execution` lines · Origin: the owner has no local GPU and no budget. The run goes on the owner's Colab Pro compute units.

**Problem.**
- **The only GPU is Colab's.** It is a Colab Pro session with an A100 80 GB, at about 7.5 compute units an hour, and 100 units a month buy about 13 A100 hours (status R: a third-party measurement, 2026-03; Colab's pricing page). A session ends when the browser disconnects or at its maximum lifetime, and the VM's local disk goes with it. Background execution needs Pro+.
- **One episode at a time is too slow.** EXP-0001 runs roughly 4,000–7,000 episodes of up to 60 model calls each. One at a time, that is 67–117 hours, about 100 at the expected ~6,000 (status M: about one episode a minute).
- **The wall-clock cap.** ADR-0007 E5 counts calendar time since run start, so the hours between two Colab sessions would count against the 96-hour cap.
- **Crash safety.** It assumed a run directory that outlives the process.

**Decision.**
- **D1 Accelerator (owner).** One A100 80 GB, nothing else. The pilot and the run read `nvidia-smi` before any episode and fail closed on any other GPU or GPU count (a 40 GB A100, an L4, an H100, two GPUs). The ledger's session record names the GPU.
- **D2 Wall-clock basis (owner: active run time only; the span rule, the heartbeat and the reading of design §8 are builder-2's).** `wall_clock_hours_max` (96) counts active run time: the sum, over the ledger's sessions, of each session's span. A span runs from the process opening the ledger to the session's last record. Every run record carries a clock; notes carry none. Time between sessions is not counted. Neither is the time between a crashed session's last record and the crash, which is at most the time between two records: the miner stamps a `heartbeat` record after every teacher call, so no stage goes long without one. The locked design's §8 ("96 wall-clock hours", "1 local GPU/accelerator node") is read accordingly: active run time, and one hosted accelerator node counts as the one node.
- **D3 Parallel episodes (the owner decided parallel episodes; the mechanism below is builder-2's).** Independent episodes run in worker processes against one `vllm serve` process, which batches their requests:
  - The parent admits every episode before it starts and records it after it ends, so the ledger has one writer.
  - Every cap check counts the worst case of every attempt in flight. While episodes are in flight, an admission a cap would block is deferred and writes nothing; the episodes in flight finish and are recorded, and only then may the admission stop the run. So the stop never cuts an admitted episode short. One clock reading decides each admission.
  - The operator may stop a session at a time limit (`--stop-after-hours`): no new episode is admitted, the episodes in flight are recorded, and the run stays running for a later session (`RunPaused`).
  - A worker process is replaced after 50 games (TextWorld's caches grow with every game a process opens).
  - Episodes run in parallel only in batches whose episodes do not depend on each other's outcomes:
    - the lifetimes of all seeds at once, and the final evaluation at once;
    - the gate in three stretches: replay and ablation of every candidate; generalization and regression of every candidate; then the interaction pairs of the eligible set.
  - A dry pass of the real gate code collects each stretch's episodes; it answers an unrecorded episode with a placeholder and runs none. A recorded gate episode that the gate's real pass does not request fails the run closed. The check reads the ledger, so it also stops every later session of that run.
  - The episodes, their keys, their settings and the decisions are the sequential run's. Only their order and concurrency differ. The scripted end-to-end tests check this: the same report and the same ledger keys, with and without interaction pairs.
- **D4 Serving (builder-2; no threshold or protocol value changes).**
  - The server loads a local snapshot of one pinned revision. These are the files `sha256_files` hashes for the run-start record.
  - It runs with `--generation-config vllm`, and every request also sends the neutral sampling values (top_p 1, top_k 0, min_p 0, repetition_penalty 1, no presence or frequency penalty). vLLM's default `--generation-config auto` would otherwise fill unset fields from the model's `generation_config.json`. Qwen2.5-7B-Instruct's sets repetition_penalty 1.05, top_p 0.8 and top_k 20, which the offline adapter's explicit `SamplingParams` never applied.
  - Batch-invariant kernels are on (`VLLM_BATCH_INVARIANT=1`), so a reply does not depend on what else is in the batch. vLLM 0.29 documents this as a beta feature, validated on Qwen2.5-7B-Instruct, that needs compute capability ≥ 8.0, which the A100 has. It may cost throughput, which the pilot measures.
  - Engine seed 0. A context of 32,768 tokens, Qwen2.5-7B-Instruct's native length, so no prompt is cut.
  - vLLM is pinned to 0.29.0, with torch 2.13.0, in their official CUDA 12.9 builds in every session, whatever the driver (a CUDA 13 driver runs them too). So are the libraries that render, tokenize and constrain a request: transformers 5.19.0, tokenizers 0.23.3, huggingface-hub 2.2.0, xgrammar 0.2.8, llguidance 1.7.6 and jinja2 3.1.6, the versions a resolver picked for vLLM 0.29.0 on Python 3.12 on 2026-10-15; TextWorld 1.7.0 and ALFWorld 0.4.2 are pinned by the package's extra. The run-start record names the installed version of each of these packages and the server's version string; every session record names its own; a resume on other versions fails closed.
  - The structured-output constraint sent to the server omits `uniqueItems`, which vLLM 0.29.0's xgrammar and guidance backends reject with HTTP 400; the miner's output schema itself and its pre-registered hash do not change. The reply is validated against the full schema, so a reply that breaks a dropped keyword (a family named twice) is a malformed teacher output, which the miner records and rejects as it does any.
  - `serve` refuses a port that already answers, unless the server there is the one it started earlier with the same command and settings and still runs; then it reuses that server. So the recorded server settings are always those of the server the run talks to.
  - Before a pilot or a run, `preflight` sends two calls outside any ledger: a ReAct reply with the stop sequence, and a structured reply under the miner's schema.
- **D5 Persistence (builder-2).**
  - The run works in a local directory. Snapshots of it go to a mirror on Google Drive, at most one a minute and always after a terminal record.
  - A snapshot is taken in the parent right after a ledger append. No file a ledger record refers to is half-written then, so the snapshot is a state the run could also have crashed in. The trajectory of an episode still in flight may be caught half-written; it has no record, and a resume replaces it.
  - Files are stored once by content hash, and each snapshot is a numbered manifest written after its files. A crash during a snapshot leaves the previous one whole.
  - A restore takes the newest whole snapshot, checks every file against its hash, and appends a `restore` note to the ledger.
  - A torn last ledger line is never salvaged silently. It can be cut off on purpose; the cut bytes are kept and a `repair` note is appended.
  - A second process taking over the mirror stops the first.
  - A restore or repair note may follow a terminal record, so a finished run restored from its mirror still loads.
  - When the last snapshot of a session fails (Drive full or disconnected), `run` and `pilot` exit with code 3 and leave `UNMIRRORED.json` in the run directory: the newest records exist only on that machine. The notebooks then never release the runtime; the owner mounts Drive again and runs `snapshot`, which clears the marker. Before every release the notebooks flush Drive (`drive.flush_and_unmount`), so the last writes reach it.
  - `mirror-check` tries the mirror's filesystem (write with fsync, replace over an existing file, read back, delete, time per small file) before the model download and any episode; on Colab only the install precedes it.
- **D6 Data (builder-2).** The frozen split and pilot manifests hash games built from ALFWorld release 0.2.2 (`json_2.1.1_json.zip`, sha256 `25171f16…44bc`; `json_2.1.1_tw-pddl.zip`, sha256 `d376c4bb…ef67`). alfworld 0.4.2's own `alfworld-download` fetches release 0.4.0's game files (`json_2.1.2_tw-pddl.zip`), whose `game.tw-pddl` differ, so no manifest game would open. `fetch-data` downloads exactly the two 0.2.2 archives and checks their sha256; `verify-data` hashes all 338 manifest and pilot games before the model download and any episode, and the pilot and the run check them again at start. The run-start record and the pilot report name the release, both archive hashes and the number of games verified. This is how ADR-0003 D8's "data-tree hash" is met, though not where D8 puts it: the split manifest is frozen and cannot carry the archive hashes. The owner accepted this reading with D4–D6 on 2026-10-15 (see the status line).

**Reason.**
- **D1.** The owner admits one well-defined accelerator, so throughput and numerics do not vary across GPU types within the run.
- **D2.** Without it, the cap would mostly count disconnected time. Active run time bounds the run's counted time, not the hours Colab bills: each session's setup (install, model download and server start, about 20–35 minutes, status M) and the work lost before a restore are not counted.
- **D3.** Worker processes keep one TextWorld game per process (TextWorld is not documented as thread-safe) and keep the parent the only ledger writer. Counting the attempts in flight keeps every hard cap a hard cap. Prefetching only dependency-free stretches keeps the run's episode set exactly the sequential one: no speculative episode is spent against the caps.
- **D4.** Without the neutral values, the server and the offline adapter would sample from different distributions under the same recorded settings. Batch invariance keeps "one deterministic execution per (task instance, condition)" meaningful when episodes share a batch.
- **D5.** A Colab VM can vanish at any moment. Snapshots taken at a crash-consistent point reuse the pipeline's existing write-ahead order instead of adding a second one.
- **D6.** The manifests' content hashes already fail closed on other data; the pinned archives make the right data the one the notebooks fetch, and the check runs before the model download and any episode.

**Research implication.**
- **Determinism.** Batch invariance holds "on the same hardware and the same vLLM version" (vLLM's reproducibility notes). The run therefore uses the same pinned versions in every session and refuses to resume on others. Colab can still hand out A100s of the same type behind different drivers; the session records name the GPU and driver of every session. A recorded episode is never re-run. The pilot's `temperature_0_repeat_determinism` measures repeat determinism under the run's own concurrency.
- **The accounting gap.** Work done after the last snapshot before a VM is lost runs again after the restore. The calls and the active time of the lost run are not counted, so each restore can under-count by up to one snapshot interval plus the time between two ledger records. The restore notes keep every restore on record; the report should list them.
- **Active run time is a weaker bound than calendar time** on how long the run takes from start to end. It is the bound the owner chose.
- No novelty or causal claim. No threshold, budget, seed, allocation or arm definition changes.

**Experiment needed.** The calibration pilot (ADR-0003, ADR-0007 E2) runs on this execution path and measures, among other things, the throughput at the chosen worker count, the calls per episode and the temperature-0 repeat determinism. The compute-cap decision (takeover note §5.12) follows it.

**Compatibility impact.**
- The ledger schema goes to 0.2: session records, a clock on every run record, heartbeats, and notes. No 0.1 ledger exists, because no run or pilot has started.
- The run-start record gains an `environment` block (the installed software and the verified data, D4 and D6), and the session record a `software` block.
- `Exp0001Run` gains `workers`, `sleep_between_retries`, `session_info`, `on_ledger_append` and `pause_when`, and binds the backend version as well as the model id, revision and backend. With the default of one worker, its episodes run one at a time in the order they did before.
- The protocol's `cap_rule` text changes and gains `wall_clock_basis`, so the run-start record changes. The manifest's `compute_cap` gains `wall_clock_basis: active-run-time`, and `run_protocol` gains an `execution` line.
- ADR-0007 E5's wall-clock clause is amended by D2, and its cap rule by D3's in-flight count.
